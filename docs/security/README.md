# รายงานตรวจสิทธิ์ ความปลอดภัย ข้อมูลส่วนบุคคล และทดสอบทั้งเว็บ (บทที่ 31)

ตรวจบนฐานข้อมูลทดสอบในเครื่อง (migration ครบถึง 20261101000002) และเซิร์ฟเวอร์แบบใช้งานจริง (`next build` + `next start`)
migration ทั้งสองไฟล์นำขึ้น Supabase จริงแล้ว ตรวจ checksum ตรงกับเครื่องทดสอบ ทดสอบแบบย้อนกลับผ่าน และตัวตรวจความปลอดภัยของ Supabase ไม่พบรายการใหม่ที่ผิดปกติ
ไฟล์ประกอบ: `rls-matrix-บทที่31.xlsx` (ตาราง x บทบาท x อ่าน/เพิ่ม/แก้/ลบ) สคริปต์ตรวจทั้งหมดอยู่ที่ `scripts/security/`

## 1. สิทธิ์ข้อมูลทุกตาราง (RLS)

- ตารางทั้งหมด 95 ตาราง เปิด RLS ครบ 95 ตาราง ผูกเขตปกครอง 47 ตาราง
- วิธีตรวจ: `rls_matrix.py` สร้างข้อมูลทดสอบของทุกตารางใน 3 เขต (A = ตำบลในเขตของผู้ทดสอบ, B = ต่างจังหวัด, C = ต่างนิกาย)
  แล้วลอง อ่าน เพิ่ม แก้ ลบ ในนามผู้ใช้จำลองบทบาทละ 1 คน (12 บทบาท) และบัญชีทดสอบ 5 บัญชี ทุกการเขียนย้อนกลับ
- บัญชีทดสอบ 5 บัญชี: เลขานุการตำบล ก1-1, จศป., การเงิน, สารบรรณ, พัสดุ
- ผล: **ไม่พบการเห็นหรือเขียนข้ามสาย 0 จุด** ทั้งบทบาทจำลองและบัญชีทดสอบ / ลบตรงไม่ได้ทุกตาราง (ปิดใช้งานแทน) /
  ผู้ดูแลระบบและส่วนกลางเห็นทุกเขตตามที่ออกแบบ / ตารางข้อมูลกลาง (ปีการศึกษา หมวด ทะเบียนวัสดุ ฯลฯ) อ่านได้ตามที่ออกแบบ
- สร้างรายงานใหม่: `python3 -I scripts/security/rls_matrix.py app3 out.json <อีเมล 5 บัญชี>` แล้ว `python3 -I scripts/security/rls_report.py out.json รายงาน.xlsx`

## 2. หน้าสาธารณะและ API

- วิธีตรวจ: `public_pii_check.py` ฝังข้อมูลที่ห้ามเผยแพร่ (เลขประจำตัว 4 ตัวท้าย วันเกิด เบอร์ส่วนตัว ที่อยู่จัดส่งข้อสอบ นามสกุล หมายเหตุ
  เลขที่ ปกศ. ชื่อเจ้าสำนัก อีเมลผู้ยื่น) แล้วค้นในทุกช่องทางที่คนไม่ล็อกอินเข้าถึงได้
- ตรวจ: ฟังก์ชันที่ anon เรียกได้ 42 ฟังก์ชัน / อ่านตรงผ่าน REST ทุกตาราง 95 ตาราง / หน้าสาธารณะ 27 หน้า (HTML + ข้อมูล RSC ดิบ) และไฟล์ส่งออก Excel 3 ไฟล์
- ผล: **พบข้อมูลต้องห้าม 0 จุด** ตารางที่ anon อ่านตรงได้มีเพียงข้อมูลอ้างอิง (ปีการศึกษา ค่าตั้ง เขตการปกครอง หน่วย บทบาท) ที่เหลือถูกปฏิเสธทั้งหมด
- กุญแจลับในโค้ดฝั่งเบราว์เซอร์: `npm run check:secrets` (รันหลัง `npm run build`) ไม่พบ (ทดลองฝังกุญแจปลอมแล้ว ตรวจพบจริง)

## 3. ข้อมูลส่วนบุคคล (เพิ่มในบทนี้)

- หน้า /privacy นโยบายความเป็นส่วนตัว (หัวข้อตามกฎหมาย เนื้อหาผู้ดูแลระบบกรอกเองที่ /app/admin/privacy)
- ข้อความแจ้งวัตถุประสงค์บนฟอร์มที่เก็บข้อมูล 5 จุด: ติดต่อเรา, ขอบัญชี, ทะเบียนบุคคล, บัญชีสมัครสอบ, ผลการเรียนของฉัน
- บันทึกการเข้าดูข้อมูลบุคคล (ใครดูของใคร เมื่อใด ดู/ส่งออก/พิมพ์/ค้นหา) อ่านได้เฉพาะผู้ดูแลระบบ ส่งออก Excel ได้
- ช่องทางขอแก้ไขหรือลบ: แบบฟอร์มติดต่อเรา หัวข้อ "ข้อมูลส่วนบุคคล (ขอแก้ไขหรือลบ)"
- อายุการเก็บ 9 ชุดข้อมูล ผู้ดูแลระบบกรอกจำนวนปีเอง ระบบแสดงจำนวนรายการที่ครบอายุ **ไม่ลบเอง**

## 5. ทดสอบเส้นทางหลัก 9 ระบบ (end-to-end)

ผ่านทั้ง 9 เส้นทาง: ทะเบียนบุคคล / ทะเบียนสถานที่ > หน้าสาธารณะ / คลังข้อสอบ ทำแบบทดสอบ / คำขอจัดตั้ง > ติดตามคำขอ / สมัครสอบ อัปโหลด ยืนยัน ส่ง /
ผลสอบ นำเข้า ประกาศ > หน้าสาธารณะ / งบประมาณ ขอใช้ อนุมัติ เบิกจ่าย / พัสดุ ใบเบิก อนุมัติ จ่าย / สารบรรณ ส่ง > หน่วยปลายทางลงรับ

## 6. ความเร็ว (สถานที่ 50,000 แห่ง ผู้สมัคร 500,000 คน ผลสอบ 500,000 รายการ)

ข้อมูลจำลอง: `scripts/security/perf_seed.sql` วัดด้วย `scripts/security/perf_check.sql` (ฐานข้อมูลทดสอบในเครื่องเท่านั้น)

| งาน | เวลา |
|---|---|
| ค้นทะเบียนวัดด้วยคำค้น / ตัวกรองจังหวัด / หน้าสุดท้าย | 0.02–0.07 วินาที (หน้าเว็บ 0.03–0.15) |
| ส่งออก Excel ทะเบียน 5,000 แถว | ฐานข้อมูล 0.15 วินาที หน้าเว็บ 0.8–1.2 วินาที |
| ค้นสนามสอบ | 0.01–0.02 วินาที |
| ตรวจรายชื่อผู้สมัคร / ค้นผลสอบด้วยชื่อ | 0.005 / 0.1 วินาที |
| สถิติผู้สมัคร / สถิติผลสอบ / ตัวเลขหน้าแรก | 0.45 / 0.55 / 0.2 วินาที (หน้าเหล่านี้แคช 5 นาทีอยู่แล้ว) |
| รายชื่อสำนักที่มีผู้สอบได้ / รายชื่อผู้สอบได้ของสำนัก | 0.3–0.4 / 0.004 วินาที |

ทุกหน้าตอบภายใน 2 วินาที ดัชนีเดิม (trigram ชื่อสถานที่ ชื่อผู้สมัคร) เพียงพอ ไม่ต้องเพิ่มดัชนี ส่วนที่ช้าแก้ด้วยการเขียนฟังก์ชันใหม่ (ข้อ 12)

## 7. มือถือและการเข้าถึง

- ตรวจอัตโนมัติด้วย axe-core (เกณฑ์ WCAG 2.1 ระดับ AA) 49 หน้า (สาธารณะ 22 / พื้นที่ทำงาน 27) ทั้งจอคอมพิวเตอร์และจอมือถือ 390 px: **หลังแก้ไม่พบข้อผิด**
- ตัวอักษร: พื้นฐาน 17 px ไม่พบตัวอักษรเล็กกว่า 13 px / มือถือ: ไม่มีหน้าใดล้นแนวนอน
- แป้นพิมพ์: Tab ครั้งแรกคือ "ข้ามไปยังเนื้อหา" ทุกหน้า กด Enter แล้วไปที่เนื้อหา ทุกจุดที่โฟกัสมีกรอบให้เห็น

## 8. รายการที่ยังค้าง / ข้อจำกัดที่ทราบ

1. **ต้องตั้งเองในหน้า Supabase** (ไม่มีเครื่องมือให้ตั้งจากที่นี่): Authentication > ความยาวรหัสผ่านขั้นต่ำ 12 และเปิด Leaked password protection
2. ผู้ใช้เดิมที่รหัสผ่านสั้นกว่า 12 ตัว ยังเข้าได้จนกว่าจะเปลี่ยนรหัสผ่านครั้งถัดไป (ระบบไม่บังคับเปลี่ยนทันที)
3. บัญชีส่วนกลางในฐานจริง (ปัจจุบัน 1 บัญชี) ต้องตั้งยืนยันตัวตน 2 ขั้นเมื่อเข้าสู่ระบบครั้งถัดไป (ต้องมีแอปยืนยันตัวตนบนมือถือ)
4. การจำกัดความถี่นับตาม IP: เครือข่ายเดียวกัน (เช่น วัดหรือสำนักงานที่ใช้อินเทอร์เน็ตร่วมกัน) ใช้โควตาร่วมกัน
5. ฟังก์ชัน quiz_start และ public_places ยังเรียกตรงผ่าน API สาธารณะได้โดยไม่ผ่านตัวจำกัดความถี่ (ไม่มีข้อมูลส่วนบุคคล แต่ quiz_start ทำให้ตารางโตได้)
6. บันทึกการเข้าดูครอบคลุมหน้ารายละเอียดบุคคล ผู้สมัคร ผลสอบ ข้อความติดต่อ การส่งออก การพิมพ์ และการค้นหาบุคคล แต่ไม่บันทึกหน้ารายการ (ตารางรวม)
7. อายุการเก็บ: ระบบรายงานจำนวนที่ครบอายุเท่านั้น ไม่ลบเอง (ตามที่กำหนด) การลบจริงต้องมีขั้นตอนอนุมัติแยก
8. ผู้รับข้อความติดต่อแบบบทบาทยังไม่แยกตามเขต (เช่น เลขานุการทุกเขตเห็นหัวข้อที่กำหนดให้บทบาทนั้น)
9. การทดสอบเพิ่มข้อมูลของ appointments, form_templates, org_units, venue_officers ในตารางสิทธิ์ ติดกติกาข้อมูลก่อนถึงการตรวจสิทธิ์ (ตรวจแยกในชุดทดสอบของแต่ละบทแล้ว)
10. ยังไม่ได้ทดสอบกับโปรแกรมอ่านหน้าจอจริง (NVDA, VoiceOver) และความเร็วกับเครื่องฐานข้อมูลจริงของ Supabase ซึ่งอาจต่างจากเครื่องทดสอบ
