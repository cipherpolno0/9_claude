## 2. กู้คืน

### กรณีซ้อมกู้คืน (ทำทุก 3 เดือน) หรือข้อมูลชุดใช้งานจริงเสียหาย

ปลายทางต้องเป็นโครงการ Supabase ที่ว่าง (ยังไม่มีตารางของเว็บ) สคริปต์หยุดเองถ้าปลายทางมีตารางแล้ว จึงกู้ทับชุดใช้งานจริงโดยไม่ตั้งใจไม่ได้

1. เตรียมโครงการปลายทางว่าง: ซ้อม = ลบโครงการชุดทดสอบแล้วสร้างใหม่ (หรือสร้างโครงการชั่วคราว) / เสียหายจริง = สร้างโครงการใหม่สำหรับใช้งานจริง
2. แก้ Secrets `STAGING_*` ให้ชี้โครงการปลายทาง
3. GitHub > Actions > **กู้คืนลงชุดทดสอบ** > Run workflow: ช่องเลขที่การรันเว้นว่าง (= สำรองล่าสุด) หรือใส่เลขของวันที่ต้องการ, ช่องยืนยันพิมพ์ `RESTORE-STAGING`
4. Workflow ทำให้: ดาวน์โหลดและถอดรหัส > คัดลอกกุญแจหลักของ Vault (ถ้าตั้ง Secret) > เปิดส่วนขยายเดียวกับต้นทาง > กู้ roles / schema / data และตั้งสิทธิ์ตามต้นทาง (`acl.sql`) ในรายการเดียว (ปิด trigger ระหว่างโหลด) > กู้ประวัติ migration > **เทียบจำนวนแถวทุกตาราง และสิทธิ์ทุกตาราง/ฟังก์ชัน/คอลัมน์กับตอนสำรอง ไม่ตรงแม้รายการเดียว = ล้มเหลว** > อัปโหลดไฟล์ทุก bucket > ลบไฟล์ที่ถอดรหัสแล้ว
5. กรณีเสียหายจริง: ตรวจหน้าเว็บกับโครงการใหม่ แล้วเปลี่ยนค่า Vercel Production (`NEXT_PUBLIC_SUPABASE_URL` และกุญแจ) ให้ชี้โครงการใหม่ > Redeploy > ตั้ง Authentication ตาม [deploy.md](deploy.md) ข้อ 3 > แก้ Secrets `PROD_*` ให้ชี้โครงการใหม่
6. ข้อมูลที่เกิดหลังเวลาสำรองล่าสุดจนถึงเวลากู้คืนจะหายไป (สูงสุดประมาณ 1 วัน) แจ้งผู้ใช้ให้บันทึกซ้ำ

ข้อควรระวัง:
- ชุดที่กู้จากข้อมูลจริงมีข้อมูลส่วนบุคคลจริง ต้องปิดกั้นการเข้าถึงเท่าชุดใช้งานจริง ซ้อมเสร็จแล้วลบโครงการนั้นหรือรันกู้จากไฟล์ทดสอบทับ
- Vault: ถ้าไม่ได้คัดลอกกุญแจหลัก ข้อมูลอื่นใช้ได้ปกติ แต่การบันทึกเลขประจำตัวประชาชนใหม่จะผิดพลาด ให้ตั้ง Secret ข้อ 1 แล้วกู้ใหม่ ห้ามสร้าง `national_id_key` ใหม่เอง (ข้อมูลเข้ารหัสเดิมจะอ่านไม่ได้)
- ผู้ใช้ต้องเข้าสู่ระบบใหม่ทุกคน และตั้งยืนยันตัวตน 2 ขั้นใหม่ถ้าย้ายโครงการ

### กู้คืนไฟล์ด้วยมือ (กรณีไม่มี GitHub)

ดาวน์โหลด artifact แล้วถอดรหัสบนเครื่องที่มี gpg และ Supabase CLI:
`gpg -d backup-*.tar.gz.gpg | tar -xzf -` แล้ว `TARGET_DB_URL=... bash scripts/ops/restore-db.sh db` และ `SUPABASE_URL=... SUPABASE_SECRET_KEY=... node scripts/ops/storage-files.mjs restore storage`

| | ชุดใช้งานจริง (ก่อนล้างข้อมูลทดสอบ) | โครงการชุดทดสอบ | รอผู้ดูแลระบบรัน workflow ครั้งแรก | |

สิ่งที่พบจากการซ้อมในเครื่อง: ต้องเปิดส่วนขยาย pg_trgm ในปลายทางก่อนกู้ (ดัชนีค้นชื่อใช้) สคริปต์จึงบันทึกรายการส่วนขยายไว้ในไฟล์สำรอง (`extensions.sql`) และเปิดให้ก่อนกู้คืนทุกครั้ง; ตาราง `document_routes` มี foreign key อ้างถึงกันเป็นวง จึงต้องกู้ข้อมูลด้วย `session_replication_role = replica` ตามวิธีของ Supabase; **สิทธิ์ (สำคัญ)**: โครงการ Supabase ใหม่ตั้ง default privileges ให้ anon และ authenticated ได้สิทธิ์ทุกตารางและฟังก์ชันที่สร้างใน public ไฟล์ schema ของ pg_dump ให้สิทธิ์ตามต้นทางแต่ไม่ถอนสิทธิ์ที่ได้เพิ่มจาก default privileges ผลซ้อมครั้งแรกจึงพบวัตถุ 447 รายการที่สิทธิ์กว้างกว่าต้นทาง (เช่น บุคคลทั่วไปเรียกฟังก์ชันภายในได้ อ่านตารางที่ซ่อนคอลัมน์ได้ทั้งตาราง) แม้จำนวนแถวและ md5 ตรงทั้งหมด จึงเพิ่ม `scripts/ops/acl-sync.sql` (สร้าง `acl.sql` ตอนสำรอง: ถอนสิทธิ์ทั้งหมดของ public/anon/authenticated/service_role แล้วให้ใหม่ตามต้นทาง รวมสิทธิ์รายคอลัมน์) และ `scripts/ops/acl-list.sql` (เทียบสิทธิ์ทุกรายการหลังกู้ ไม่ตรง = ล้มเหลว) ไฟล์สำรองที่สร้างก่อนแก้ไม่มี `acl.sql` สคริปต์กู้คืนจะหยุด ให้สำรองใหม่ก่อน
